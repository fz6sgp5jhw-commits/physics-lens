# Physics Lens: architecture and internals

Reference for Claude Code. Read only the section you need (`grep -n '^## ' docs/architecture.md`). Lasting rules are in `CLAUDE.md`; current work is in `ROADMAP.md`. Older design history: the Rotation Lab design doc (https://claude.ai/artifact/2zgFj7tQRXbpbTT442NFcQ) and `docs/phase-e-design.md`.

Core idea: every diagram the student builds produces an equation (free-body diagram → ΣF = ma; motion ladder → v = dx/dt, a = dv/dt; later energy bar chart → before + work = after; momentum diagram → p before = p after).

## Files
- `index.html`: layout and all CSS. One set of rules, in the order of the page (app bar, panels, buttons and fields, givens, conditions, library, sheet, work, canvas card, drawing, side panels, drawer, dialogs, calm mode); colours, pixel frames (`--frame-*`, `--btn*`) and the star shape (`--star`) are variables on `:root`. A Content-Security-Policy `<meta>` allows only the app's own files (plus inline styles and `data:` images). Layout (Phase 2): one workspace. Left: problem bar (units, text), givens strip (chips; "+ Add a given" opens the palette; found values show "found · (a)"), the canvas card (Setup / Forces / Motion, Replay, Library). Right (sticky, 460px): only the open stage's panels, chosen by `data-stage` on each card (`.off` hides the rest): 0 Setup → inspector, sliders, graphs and a setup checklist (`#setupGuide`); 1 Forces → free-body builder; 2 Conditions → `#condCard` with the calculus ladder (`#calcCond`); 3 Solve → the sheet (`#calcSolve`, targets, Hint, Show me, one column of cards in solving order, the work under the latest solved card), What matters, Path. The equation library is a drawer (`#libDrawer`, Library button, Esc closes).
- `js/packs/` (phase C2): subject packs. `index.js` lists `PACKS`, `mergePacks()` merges them (refuses an id collision or a missing `<pack>_` prefix; mechanics is `bare`; `py` defaults to the id; `sample` per quantity) and `attribution()` lists licences and outside sources. `mech.js` is all mechanics data: quantities, equations, units (chapters, with their hooks), the diagram library, practice (each `original: true` or with a `source`). A new subject is a new pack file listed in `index.js`; `tests/core-packs.test.js` proves it with `tests/fixtures/demo-pack.js`.
- `js/data.js`: merges the packs and exports `VARS`, `EQS`, `CHAPTERS`, `COMPONENTS`, `PRACTICE`, `PRINT_ORDER`, `SAMPLE` (from each quantity's `sample`), `DIMS`, `V`, `fmt` (now in expr.js), `sizeSI`, `withUnit`; derives every solver from its one-line `eq` and checks units at load
- `js/expr.js`: expression engine: parses `sub` templates, evaluates them with numbers, simplifies them with symbols (canonical rational form), prints them, checks units
- `js/app.js`: state, rendering, path finding, solving, diagrams, graphs, practice bank, setup checker, effects
- `js/systems.js` (phase C1): which equations must be solved together. `matching` (Hopcroft–Karp), `structure(eqs, unk)` → `{ blocks, missing, under, extra }` (blocks are Tarjan SCCs in solve order), `readyBlocks`, `eliminate` (exact elimination over Z = 0 rational forms). Pure, tested in Node (`tests/core-engine.test.js`).
- `js/recognize.js` (Phase 4): freehand strokes. `classify(points)` → line / arrow / box / loop / closed (ask) / curve / unknown; `recognize(points, scene)` → `{ options, ask }` or `{ options: [], why }`. Every threshold is in `RULES`. A box is told from a loop by how much of its tightest turned rectangle it fills (so a box drawn tilted on a ramp still reads as a box). Tested with recorded strokes (`tests/strokes.json`, placed by `tests/strokes.js`).
- `js/torque.js` (Phase 5): extended free-body diagrams for a beam or a disc, as template strings: force kinds (`KINDS`), directions (`DIRS`, slants at φ to the beam, tilt β via `TILT`), a point's position from the left end (`position`: centre ½L, ends, pivot, or d_P/d_m/d_T/d_F measured from the end in `S.fbd.from`), each force's parts (`parts` → x and y components, lever arm r, sin φ, τ = r·F·sin φ), the equations (`equations` → ΣFx, ΣFy, Στ about the axis, or Στ = Iα) and the checker (`check`). No state: app.js passes the body, its forces and `{ tilt, axis, from, dyn, radius }`.
- `js/setup.js` (Phase 6a): drawing-first setup. `VOCAB` is the one data table of part cards (rod, block/particle, disc, string, pivot, pulley, the whole system): groups (`q`, `when` = a fact the group needs to show), choices (`term`, `plain`, `adds`, `as` for conflict sentences, `needs` / `clash` = [fact, why]), assumed defaults (`overturn` words). Facts come from the drawing (`CTX`, `ctxOf`: onRod by geometry, string, pinned, support, surface, disc, moving/slides from v or a arrows, wound). `createSetup` owns the state (`S.df`: `done`, `parts[id] = { kind, n, title, answers, off }`, `view` = a part id, 'summary' or null, `closed`): **Done drawing** (`#doneDraw`) gives each part a dot (`[data-dot]`, drawn by `decorate` from build's `afterRender`, only in drawing-first mode) and a title numbered left to right; the card (`#dfCard`, `[data-group]` / `[data-choice]`, 'unsure' always offered) glows its part and dims the rest (`.dfglow`, `.dfdim`); the counter `#dfCount`; the summary (`#dfSummary`, `#dfSumBtn`) opens by itself when every part is set and its `#dfClose` is disabled while `conflictsOf` finds any.
- `js/build.js`: the drawing canvas (SVG): tools (select, pen, erase, shapes, v/a arrows, ω/α spin arrows, force kinds, centre of mass), snapping, resize handles (ramp angle ● and length ■, block, ball, table), arrows turned by dragging their tip (they click onto named directions within 12°, otherwise keep a custom angle), undo history, contacts, templates. The toolbar markup is built by `renderBuildUI()` in app.js.
- `js/field.js`: the background: a pixelated glowing vector field with drifting charges, stars, a pixel sun and moon; the cursor is a test charge; `pulse()` on each solved step. API `createField(arrows, trails) → { pulse, setCalm, running }`. Calm mode freezes it.
- `sw.js`, `manifest.webmanifest`, `icons/`: installable offline app (`sw.js` handles only same-origin GET requests)
- Safety: text the student types reaches HTML only through `esc()` (top of `app.js`) or `textContent`. The work panel is written through `startWork` / `workLine` / `workBlock` / `finishStep`, shared by equation, symbolic and ladder steps; `checkWithNumbers(last)` re-runs the path at random values for all of them.
- Clear all removes the drawing (undo brings it back), the drawn forces and every given, target and equation; switching units keeps the drawing and re-adds its quantities if the new unit uses them (`syncDrawingGivens`).
- No web fonts: system UI font for text, system monospace for equations and numbers.

## Behaviour that must keep working
- Modes (Phase 6a): drawing-first (default; `S.mode = 'draw'`, body class `mode-draw`) or guided (today's flow). `#modeBtn [data-mode]` in the app bar; guided is stored as `pl-mode`, and choosing drawing-first removes the key. Drawing-first switches to the torque unit and hides `.guided-only` (tracker, problem and givens cards, canvas tabs, Library, Practice bank, the stage cards in the right column); `.draw-only` is hidden in guided mode. Tests open guided mode unless `openApp(…, { mode: 'draw' })`.
- Stages (Phase 2): the tracker `#steps` holds four `[data-stage]` buttons and the pinned `#sheetTab`. `stageChecks()` → [Setup: a drawn body or a given you added; Forces: a ΣF written from a checked free-body diagram or a drawn v/a arrow, `null` when nothing is drawn (no star, doesn't block); Conditions: `S.condOk`; Solve: every target found]. Hybrid gating: `reach()` = one past the first stage that hasn't passed; `openStage(i)` refuses stages beyond it, except Solve, which opens read-only (`#sheetLock`, `#sheetWin.locked`) and `solveLocked()` stops solve, Show me, Hint, ladder moves and Combine. The canvas tabs Setup / Forces open stages 0 / 1; ✓ conditions moves on to Solve when it's unlocked.
- Units (chapters): Inclines & Newton's laws, Tension & pulleys, Pushed blocks, Rotation kinematics, Torque & equilibrium.
- Givens come from a quantity palette: size + unit + **direction toggle**. The direction sets the sign; students never type minus signs. Values are stored in SI, signed.
- Conditions: choices (friction, direction of motion), locked assumptions, and **hidden givens** ("starts from rest" adds v₀ = 0, labelled "from condition").
- Library: one long document per unit. Equations that don't fit the conditions grey out with the reason; equations with one solvable unknown glow (only after conditions are confirmed).
- Sheet: gathered equations, targets (a), (b)…, solve buttons, reachability status, hint (names the missing link, never the equation), Show me (gathers + solves the shortest path). Cards are in solving order, numbered by their path step, and say which earlier steps they used (`usesHTML`).
- Parts: `finishStep` tags each found value and path entry with `part` (the target it found, else the target being worked on). ↺ on a solved target (`clearPart`) clears that part and every later step after `ask()`; `beforeClearing()` asks before a given, condition, ΣF or Clear all wipes solved steps. `ask(title, msg, yes)` is the dialog with Cancel (`#dlgCancel`).
- Settled by the drawing (`drawnConds`, `syncDrawnConds` in the build `onChange`): a body on a surface sets friction from the surface's "rough" property; v drawn up/down the slope sets "Moving". Conditions shows these as settled, without buttons.
- Functions of time (Phase 3): typed in one box (`#edFn`); `X.parseFn(text)` → `{ poly, consts }` reads numbers, t, powers (t², t^2), brackets, / and one-letter constants (Greek words like beta work); each constant must multiply exactly one power of t to the first power, so `registerCustom` can give it one unit (`unitPer(id, k)`). `fnPreview` shows how it was read. `S.funcs[id].text` keeps what was typed.
- Between two moments (Phase 3): `S.span = { A, B }`, each `{ x: 't' | rung, mag, dir }` (size + direction, no typed signs); B is the first time after A. `CHAPTERS.rotation.spanVars` maps each quantity (`dth`, `nrev`, `dtrav`, `wavg`, `aavg`) to the function it needs (θ(t), or ω(t) for α_avg). `moves()` offers a `span` move for span quantities that are targets once both moments are set and the needed functions are known; `spanMath(x, P)` is the single source of the math (exact Rats; also used with numbers by `routeStep`), `spanOp` writes the work, `renderSpan` draws `#spanCard`. A turning point of ω(t) inside the interval adds a note with the net angle and the angle travelled.
- Diagram library (Phase 4): `COMPONENTS` in `data.js`, one entry per part (surface, ramp, block, particle, ball, wheel, rod, pulley, string, spring, pivot, force, v, a, omega, alpha) with its standard drawing (`draw`, SVG in 80 × 50), meaning, properties → variables, connections, arrows, equations (`eqs` = EQS ids; `more` = relations not in the library yet), one `check` line and the toolbar `tools` that draw it. `compHTML(k)` renders a card for the **Diagrams** drawer (`#diagDrawer`, `#diagLib`; `setDrawer(open, id)` keeps one drawer open) and the hover card (`#compCard`; tools with a card carry `data-tipkey` instead of `title`).
- Pen and recognition (Phase 4): the pen stroke goes `build.readStroke` → `recognize(points, build.scene())` → app `onStroke(res, xy, place)`: one option is placed at once, several ask through `#choosePick`, none says `why`. `build.place(option)` makes the standard shape (ramp angle from the stroke, bodies snapped from a little further away, a hanging block under the pulley, strings joined over a pulley, v/a snapped to named directions and passed to `onVector`). `build.stroke(points)` and `build.toScreen(x, y)` are for tests.
- A point on the wheel (Phase 4): in Rotation a wheel shows **◎ a point** (`wheelButton`) once ω (`w`, else `w0`) or α is known, or a spin arrow is drawn on it (sign from the arrow, size from `SAMPLE`). `pointMath(s)` evaluates R7, R8, R9, R11 through their `solve[x].f` (the templates) and gives the vectors for P at the top of the rim: along the path is (−1, 0) for counterclockwise, a꜀ points down to the centre; the accelerations share one scale. `pointPanelHTML` shows the equations with numbers when r, ω, α are numeric; **+ Add these to my sheet** (`#ptAdd`) turns on `rim` and gathers them.
- Forces optional (Phase 4b): a chapter with `forcesOptional` (rotation: kinematics only) returns `null` for the Forces check when nothing earns it, so a drawn wheel never locks Solve; an ω/α arrow still earns the star.
- This problem row (Phase 4b): a condition with `ask: [label, [[value, words]…]]` in `CHAPTERS[x].conditions` is also asked in Setup (`renderKind` → `#kindRow`, `setKind`), so the function box (varA) and r (rim) are there while givens are entered. Conditions still lists them. A wheel's or ball's ω/α arrow passes the Forces stage as its motion diagram.
- Torque & equilibrium (Phase 5): `dyn` (This problem: equilibrium or spinning up), `shape` and `axis` (named values: compare with `condIs`, not `!!`); a drawn wheel sets shape = disc, a pinned rod sets axis (centre or other). In this unit `build.bodies()` includes rods (frame `beam`, with `pivot`, `pinAt`, `pinU`, `ang`) and wheels (frame `disc`); in equilibrium hung blocks are loads, not bodies (`fbdBodies`). `isExt(b)` routes the Forces panel to `renderExtFBD`: `addExtForce` (the hinge adds H_x right and H_y up; a beam force keeps the `u` where its drag started; a disc's cord goes to the rim on the string's side), `S.fbd.from[id]` (left/right end), `S.fbd.opts[bodyId] = { tilt, axis, why }`, `axisKey` (default the pivot, else the left end; a disc always its axle), `setAxisAt` (axis tool → nearest named point), `pointU` (draws a point to scale once L and its distance are numbers). Write adds the equations with key `fbd:<body>` (so the Forces star works as before); torque equations show the unit N·m. `foundDir` adds a found force part's direction to the knowns (negative → explained). Library equation ids must not look like `G<n>` (generated ids): the beam geometry is `GEO1`, `GEO2`. The toolbar shows the beam and disc templates only in this unit, and the four older ones elsewhere (one more row would push the page past 900 px).
- Systems of three (Phase 5): `triples()` finds three linear equations whose unknowns are three quantities, two in each, and offers a `sys` move only for unknowns that survive elimination (`solvesFor`, cached in `SYS_OK`; dependent sets like K1, K2, K4 are skipped). `eliminate()` solves one equation for an unknown and substitutes it into the others until one equation is left; `combine()` and the sheet's **Combine them** use it for two or three equations (`sys.eqs`, `sysLabel`).
- Calculus ladder strip (`calcHTML`): when `varA` is on or a function of time exists, the rungs (θ → ω = dθ/dt → α = dω/dt, or Δx → v → a) with what is known on each, and the start values ∫dt needs.
- System detection (general): any two sheet equations with the same two unknowns → "Combine them" solves one for an unknown and substitutes it into the other (symbolically), adding the combined equation to the sheet.
- Diagram: clickable points (start, end, stop), force arrows in free-body diagrams, labels; library outlines the related equations. Replay with ghost frames and graphs.
- Practice bank: loads problem text only; "Check my setup" grades givens (missing, wrong value, backwards direction, extra), conditions and targets against an answer key.
- Look: "pixel night" skin (2026-11-05): felt-blue notched pixel frames, gold stars and moons, pixelated glowing vector field (`field.js`, drawn at 1/3 resolution). One colour per variable state everywhere: given cyan `#4fd1ff`, found amber `#ffd166`, target pink `#ff6bd6`, unknown grey. Hints and feedback appear in the assistant line under the app bar. Error dialogs keep their playful wording ("ILLEGAL OPERATION") with a plain icon. A solved problem pulses the field and shows a brief SOLVED.
- **Calm mode** freezes the field into one still frame and turns off every animation (also honours "reduce motion"). It is remembered across visits.

## Conventions and internals
- **Math is computed by code, never guessed.** Each equation is one line, `EQS[id] = { eq: '{W} = {m}{g}', kind: 'law' | 'rel' | 'def', cue, … }` (phase C1). At load, `data.js` derives `vars`, `form` and, per variable, `solve[var] = { steps, sub, guard?, pick?, alt?, note? }` from `eq` with `expr.js` `isolate()` (printed by `showTree`); the data keeps only `pick`, `guard`, `alt`, `note` (or hand `steps`), and `solve[var] = null` for a variable never solved for. An equation that can't be rearranged throws at load with its id and variable. `steps` are the isolation steps with a plain-English `why`. `sub` is the plug-in template with `{var}` slots and is the **single source** of the answer: `expr.js` evaluates it for numbers and simplifies it for symbols. Don't write arithmetic anywhere else.
  - `guard(v)` → a physics-specific `err(...)` or null (generic "… is zero" and "square root of a negative" messages come from the engine).
  - `pick(v, [plus, minus])` → `{ branch: ±1, note }` for templates with `±`; `alt: [{ when, sub, note }]` for special cases (a = 0 in a quadratic); `note(v, value)` for a remark under the answer.
  - `sol.f(v)` is derived at load time and returns `{ value, note, branch, tree }` or `{ error }`. Loading `data.js` throws if any template's units don't match the variable it solves for.
- Motion ladder (Phase B): `CHAPTERS[x].ladder = { rungs: [position, velocity, acceleration], start, zeroNote }`. Functions of time live in `S.funcs[id] = { poly, from: 'given' | 'ladder', step }`; a polynomial is an array of rationals (`p[k]` multiplies tᵏ), so coefficients can hold symbols. Path finding works over *moves*: equations plus ladder moves (`deriv`, `integ` (needs the start value), `eval` at a known t, `solveT` (first positive root; others are listed as rejected), `start` = value at t = 0). Targets can be scalars, `fn:<id>` (a function of t) or "the time when X = …" (target t, with X at that moment as a given). The "varies with time" condition (`varA`, rotation for now) greys out the constant-acceleration equations.
- Phase C: the Diagram window has tabs **Motion** (replay + sample-value sliders for symbols), **Build** (`js/build.js`) and **Forces** (free-body builder in app.js: `DIRS` named directions per body frame `slope`/`flat`/`hanging`, `FKINDS`, `components()`, `fbdCheck()`, `fbdEquations()`). Equations written by the app are registered in `EQS` as `{ generated: true, Z, vars, … }` (Z = 0, solved by `X.solveLinear`); `solveSym()` solves generated equations and any equation whose inputs include functions of t. Functions of time are rationals in the symbol `t` when needed (`polyToRat` / `ratToPoly`). A letter in a function's coefficient box (k in F = kt) becomes a new symbol `c_<name>` with its own unit. On inclines the student picks the axis (+ down or + up the slope); equations that assume + down the slope grey out when it's + up.
- Phase E2 (draw first): the canvas opens in **1 · Setup**. Shape properties name quantities (`PROP_VARS`: a ramp's angle θ, a block's mass m); drawing the shape adds them as givens `from: 'drawing'` (symbols until given a number by clicking the label or chip; removed with the shape; a numeric θ re-angles the drawn ramp). **2 · Forces** fades the setup and draws the free-body diagram on it: drag from a body, the arrow snaps to the body frame's named directions (`dirVectors()`), and a picker (`#forcePick`) asks which force it is. Drawn forces join the collection as chips (`#forceChips`). ΣF is written only when the student presses Write. Inclines have μs and an "at rest" condition (a = 0; kinetic-only equations grey out); `CHAPTERS.incline.statics` drives "Does it move?" in What matters (numbers: compare f with μs N; symbols: the threshold, e.g. μs ≥ tan θ).
- Phase D: **scenario tables** (`S.scen = { cols, rows }`): a given entered with the editor's "Scenario table" kind is a symbol and a column; the problem is solved once with symbols and each row is evaluated from that one answer (row 1 sets the typical values). **Ranking targets** `rank:<id>` (known once `<id>` is found and ≥ 2 complete rows exist; Show me works toward `<id>`). The **What matters** window replays the path with every nonzero given as a symbol (`replayAll()`) to list what the answer depends on, shows exact **limiting cases** (`X.limit(r, id, 0 | Infinity)`), the scenario results and per-row **assumption checks** (`CHAPTERS[x].checks = [{ when, sub, what, judge(x, v) → ['ok' | 'barely' | 'fail', text] }]`). Path finding has a `sys` move: `systems(eqList, ks)` in app.js asks `js/systems.js` for the blocks that can be solved now (matching + strongly connected components, any size); a block is combined by exact elimination (`combine` → a generated equation) and then solved, so Show me handles systems. `findSystem` offers the same on the sheet ("Combine them"). The free-body builder knows contact forces between touching blocks (`build.touching()`) and checks them as a third-law pair (same symbol, opposite directions).
- Units (phase C1): `expr.js` `UNITS` gives every unit its dimension over m, kg, s, A, K, mol and its size in SI; prefixes n μ m c k M; `parseUnit(u)` → dimension, `unitFactor(u)` → SI size, `dimEq` compares all six bases, `dimStr` names N, J, W, Pa, C, V, Ω, F, T, H. Conversions shown to students stay per quantity (`VARS[x].units`). °C is the one offset unit: `toSI(x, u, { absolute })` / `fromSI` add or take off 273.15 only for an absolute temperature (`VARS[x].absolute`) in °C on its own; ΔT and J/(kg·°C) convert by 1. `data.js` `sizeSI(id, mag, unit)` converts a given and `withUnit(id, x)` prints an answer (also in °C for an absolute temperature).
- Template syntax: `{id}`, numbers, `½`, `+ − ±`, `/`, implicit multiplication (left to right), `²` `³`, `√(…)`, `sin cos tan` and `sin⁻¹ cos⁻¹` (angles in degrees, like `inc`), `(…)` and `[…]`.
- Symbols as givens: a symbol stands for a positive size; the direction toggle carries the sign. It still has a typical value (`SAMPLE`) used only to choose roots and signs and to draw the diagram. Symbolic answers show "PUT IN WHAT YOU KNOW", "SIMPLIFY" and "CHECK WITH NUMBERS" (the whole path re-run with numbers at random values, compared with the simplified answer).
- Unit hooks (phase C2): what differs between units is data on the unit (`CHAPTERS[x]`), read by `hook(k)` in app.js with a default in `HOOKS`: `startCond`, `slopeAxis`, `extended`, `points`, `angular`, `posLabel`, `flatPlus`, `presets`, `sim`, `stuck`, plus `drawFirst` (the drawing-first unit) and `diagram` (which motion picture). A unit with no `kin` has no motion picture or replay. `app.js` names no unit (tested).
- Sign conventions are explicit per unit (`CHAPTERS[x].axis`, `dirs`). Inclines: + is down the slope. Pulleys: + is forward (m₂ falls). Rotation: + is counterclockwise.
- Square roots and quadratics pick a root deliberately and explain it in `note` (first positive time; velocity sign from the direction of motion; conditions can supply the initial-velocity sign via `__u0sign`).
- Unit-specific wording uses `nm(id)` and `dr(id)` in app.js (names and direction words can be overridden per chapter). Don't read `VARS[id].name` directly in the UI.
- Text style in the UI: plain, short, second person; error dialogs are playful but always explain the physics.
- Custom-angle forces: `f.dir = 'custom'` with `f.ang` in degrees from the body's ∥ axis toward ⊥ (`dirOf`, `angleOf`, `customVec` in app.js); components are numeric cos/sin. The checker flags them where physics requires a named direction (gravity, normal, friction).
- A drawn velocity arrow on a slope settles the "Moving" condition (`drawnConds`); `onVector` only warns when v isn't along the slope.

## Drawing-first tools (phases 6b, 7 and 8a)
- `js/tools.js`: `createTools` owns the active tool (`data-dftool` buttons in `#dfTools`), a capture-phase pointer handler on the canvas SVG (tools register `{down, move, up}`; `down` returns a state object to keep dragging, nothing to finish), and `ask()`, the small question box (`#dfPop`, `#dfPopIn`).
- `js/connect.js`: connect tool and `conn` shapes (`ends [a, b]`, `u` along the rod); `connEnds`, `rodProject`.
- `js/knowns.js`: `createKnowns` renders `#dfKnowns` and supplies the card extras (names, freedoms) through `setup.js`'s `ext` hook. `NAMEABLE` is the table of nameable quantities; `parseEntry` refuses wrong-kind values.
- `js/toolkit.js`: everything in phase 7, stored in one `tk` shape (`shape.d`); `S.tk.state()` returns it. Points of interest (`r:<rod>:<u>`, `b:<id>`, `o`) are the snap targets for gaps, coordinates and the rotation axis.
- `js/algebra.js` (phase 8a): the formula sheet and the algebra workspace (`#dfWork`, `S.ws.state()` gives the lines as text). Nodes `num {v, s}`, `sym {id}`, `add`, `neg`, `mul`, `div {n, d}`, `pow {b, e}`, `sqrt`, `fn`; `parse` reads Python-style input and the app's notation (`{id}`, ², √, ½); `print` writes one line (text or HTML). Ids are Python-style (`m_1`, `theta`, `I_cm`); `toId` maps any spelling to one and `display` back. `applyOp(eq, op, at)` with `at = {side, i}` for one term or `null` for both sides; `simplify` round-trips through `expr.js` with ids under `ws:`. `sheet(query, n)` is the library regrouped by section title, plus I = Σ m r² with n terms.
- Tests: `tests/drawfirst-knowns.test.js`, `tests/drawfirst-toolkit.test.js`, `tests/drawfirst-algebra.test.js`.
